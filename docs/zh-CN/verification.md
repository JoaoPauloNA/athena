# 验证 — claimed vs verified（声明 vs 实证）

> 为什么 Athena 需要验证器、目前的功能，以及走向完全确定性验证的路线。

## 动机

智能体 CLI 经常在没有真正完成时报告"完成，测试通过"。2026 年的评估
证据令人警醒：被广泛引用的基准测试中，相当一部分"通过"对应的任务
实际上从未被解决；学术界已经为这一现象命名（*"Confident and Wrong"*、
*"Silent Semantic Failures"*）。由智能体厂商自建的评测框架在结构上
倾向于标记成功——中立的验证层不存在这种利益冲突。

Athena 的验证器用于在本地、按 provider 度量 **claimed**（智能体声明的
结果）与 **verified**（可实际确认的结果）之间的距离。

## 两层设计，规则不同

| 层 | 工作方式 | 角色 |
|---|---|---|
| **咨询式验证器**（已实现） | 由低成本模型（优先免费档，如 opencode free）阅读执行者的报告与项目证据，给出真/假判定。防串通：验证器绝不使用与执行者相同的 provider。判定为假 → 退回修正；连续两次为假 → 上报给编排者/人类。 | 分诊。不单独阻断，不产出公开数字。 |
| **确定性验证器**（已实现） | 真实重跑报告所声称的内容（仅限白名单中的测试/lint 命令，不经 shell，逐命令超时），对比真实退出码，并检查声称为"已创建"的文件是否真实存在。**链路中不含任何模型**——用 AI 评判 AI 会摧毁数字的可信度。 | 产出可信 claimed vs verified 指标的层。结论明确时优先于咨询层。由 `ATHENA_VERIFY_MODE=auto|deterministic|advisory` 控制。 |

即使确定性检查落地后，咨询层依然有用：许多任务没有可自动化的判定
标准（文档、配置、探索），而低成本分诊可以避免把付费模型的额度浪费
在验证上。

## 路线图

- [ ] 按 CLI 持久化判定结果 → 个人可信度排名（本地 claimed vs
      verified 比率）。
- [ ] 确定性模式：执行报告所声称的内容并对比退出码；真实 `git diff`
      对比声明的文件范围。
- [ ] 在 `run_combo` 与 `deliberate` 中支持 `verify=true`。
- [ ] 更长期：带隐藏判定标准的任务套件（智能体声明成功时从未见过的
      测试），从而产出每个 CLI 可公开对比的虚假成功率。
